### 計測方法

- **コールド起動**: 反復ごとに新規ブラウザコンテキスト（HTTP キャッシュ空）で `goto` し、Python 側が `window.requestRender` を登録して操作可能になるまで。
- **ウォーム起動**: 同一コンテキストで1回読み込んでキャッシュを温めた後、反復ごとに新規ページで再ナビゲーション（HTTP キャッシュ有効）。Python／Pyodide の初期化は毎回走るので、短縮されるのはダウンロード分のみ。
- **描画**: 実行時に生成した 10,000 行（X 1列 + Y 5列）の CSV を使用（コミットしない）。系列カード5つ（X=x列、Y=y1〜y5）を設定。キャッシュを温めたコンテキストで反復ごとに新規ページ。
  - 初回: ファイル選択 → 自動読込 → 最初のプロット表示まで。
  - 設定変更: タイトル入力の `input` イベント発行から、`#plotArea` に新しい画像が表示されるまで（ページ内 `performance.now()`）。250ms のデバウンスを含む。
  - 保存: 保存ボタンのクリックからダウンロード開始まで（PNG）。

### 分析

プロファイリング調査（A/B、n=4〜6）で、起動の差の由来を切り分けた。

- ウォーム起動がベースラインより約 +0.5〜0.6 秒遅い差は、ランタイム自体に由来する。内訳の目安は、Pyodide 314 / Python 3.14 の起動で +150〜170 ms、パッケージの読込で +100〜140 ms、`import matplotlib` で +190〜250 ms、`import pandas` で +約100 ms。
- PyScript を介さない素の Pyodide ページでも同じ差が出る。アプリ側のコードが起動時間を増やしているわけではない。

Phase 1 で行った改善:

- openpyxl の遅延導入: バージョン固定の wheel URL と `packages_cache = "passthrough"` により、起動時に micropip を使わない。コールド起動で約 -340 ms（移行直後 4,076 → 3,650 ms の大部分）。代わりに、初めて .xlsx を読むときに wheel を取得する（上表の 336 ms を含む）。
- 保存・描画前に matplotlib 3.10 の `PlaceHolderLayoutEngine` を外す: 描画・保存で約 -65 ms、出力はバイト単位で同一。
- Agg バックエンドを使う（`matplotlib_pyodide` のバックエンドを使わない）。
- 日本語フォントを Cache Storage に保存する: 2回目以降の訪問では約16 MB の再ダウンロードが発生しない（E2E テストで確認）。

ベースラインとの比較では、起動（コールド・ウォーム）、再描画、保存はいずれも悪い。移行直後よりは改善したが、ベースラインには戻っていない。要件（8章）の「起動時間を F6 の現状値より悪くしない」は満たしていない。初回ファイル読込 → 最初のプロットは良い（上の注記のとおり参考値）。

**決定（2026-10-08、オーナー）**: ウォーム起動に残る差（約 +0.5 秒）は実行環境（Pyodide 314 / Python 3.14）自体のコストとして許容する。以後の要件8章の基準値は、この「Phase 1 後」の値とする（docs/REQUIREMENTS.md 8章に注記済み）。

### 分析

悪化した項目は2つで、どちらも保存 DPI の既定が 120 → 300 になったことによる（起動・再描画・xlsx 読込は Phase 2 後と同等）。

- **保存（PNG）+65%**: 300 dpi は 120 dpi の 6.25 倍の画素数（8×6 inch で 2400×1800 = 4.3 MP に対し 960×720 = 0.7 MP）。同じ設定で 120 dpi に戻した値は 246 ms（Phase 2 後の 246 ms と同じ）なので、ランタイムや生成スクリプトの増加による劣化はない。画素数が 6.25 倍になっても時間は 1.6 倍にとどまる。固定費（スクリプトの生成と実行、系列の描画）が大きく、画素数に比例する部分（Agg のラスタライズと PNG のエンコード）は一部のため。
- **編集モードの実行 +32%**: 編集モードのスクリプトは、末尾の `fig.savefig(...)` を含めて全体を実行する。Phase 3 から生成コードの `savefig` が既定 300 dpi になったので、その分の PNG 書き出しが増えた。DPI を 120 にして同じ計測をすると 439 / 425 / 443 ms で、Phase 2 後（438 ms）と同じ（確認用に3回測った値）。

悪化していない項目の補足:

- **日本語フォントの変更（16.5 MB の OTF → 5.7 MB の TTF、転送は約 3.2 MB の brotli）**: コールドキャッシュでも、Python の準備完了までにフォント取得がほぼ終わる（ナビゲーション開始 → `ready` が 3,622 ms、準備完了からの追加待ちは 67 ms）。取得は Pyodide の起動と並行して進むため、起動の体感を延ばさない（コールド起動 3,564 ms は Phase 2 後と同等）。以前は 16.5 MB を取得していたので、初回訪問のダウンロード量は約 1/3 になった。2回目以降は Cache Storage から読む点は変わらない。
- **欧文フォントの初回選択（Arimo）**: 初回（取得あり）と2回目以降（Cache Storage から）で差がない（468 ms と 467 ms）。選択からフォントの登録完了までが約 23 ms で、250 ms のデバウンスの間に終わるため、描画は取得を待たない。フォントが約 0.3〜0.5 MB と小さいことと、デバウンスと並行して取得を始める作りのため。
- **クリップボードへのコピー**: 422 ms で、300 dpi の保存（405 ms）とほぼ同じ。PNG の生成が大半で、クリップボードへの書き込みは十数 ms 程度とみられる。
- 保存設定（`save.*`）の変更は画像を再描画せず、コードだけ更新する（計測行は設けていない）。

### 一回限りの確認: ラスタ画像の画素数の上限（`formats.MAX_RASTER_PIXELS` = 100,000,000）

実アプリ（Chromium、Pyodide）で、上限付近の PNG 保存を試した。10,000 行 × 5 系列のデータで、図の大きさ（inch）と DPI を設定してから保存ボタンを押した。メモリは、Pyodide の WebAssembly メモリのバイト数（`WebAssembly.instantiate` の結果から `exports.memory` を捕まえて `buffer.byteLength` を読んだ）。保存前と保存直後の値。

| 設定 | 画素数 | 結果 | 時間 | 出力ファイル | wasm メモリ（保存前 → 後） |
|---|---:|---|---:|---|---:|
| 8×6 inch、1200 dpi（9600×7200） | 69.1 MP | 成功 | 2.1 秒 | 4.2 MB | 108 MB → 442 MB |
| 10×10 inch、999 dpi（9990×9990） | 99.8 MP | 成功 | 3.2〜3.3 秒 | 6.8 MB | 130 MB → 599 MB |
| 10×10 inch、1000 dpi（10000×10000） | 100.0 MP（上限ちょうど） | 成功 | 3.2 秒 | 6.8 MB | 130 MB → 600 MB |

- どれも、メモリ不足やクラッシュは起きなかった。コンソールエラーもない。画像の大きさは、ファイルを開いて指定どおりであることを確かめた。
- 上限付近では、RGBA の画素バッファ（1画素 4 バイト、100 MP で約 400 MB）が wasm のメモリに載るため、wasm メモリは約 600 MB まで広がった。wasm のメモリは縮まないので、保存後もこの大きさのまま残る。JS ヒープ（`performance.memory`）は約 93〜98 MB で変わらない。
- この Mac（24 GB）の結果。メモリの少ない端末（スマートフォンなど）では、600 MB 級の確保が失敗する可能性があるが、今回は確かめていない。上限（1億画素）の変更は不要と判断し、触っていない。

### 分析

Phase 3 後より 5% を超えて悪くなった既存項目は無い（日本語フォントのコールド取得の +2% は、jsDelivr からの実ダウンロードを測っているためのぶれの範囲）。Phase 4 の読込設定（読み飛ばし・桁区切り・小数点・コメント）は `read_csv` の引数が増えるだけで、日時の認識は文字列の列だけを調べるため、数値だけの CSV の読込（「初回ファイル読込」177 → 178 ms）には影響していない。

- **参考値「欧文フォント初回の選択 → ready」+48%（23 → 34 ms）**: jsDelivr から約 0.3 MB を取得する時間で、ネットワークのぶれ。デバウンス 250 ms の間に終わるため、プロット更新（459 ms）には影響していない（Phase 4 で欧文フォントの処理は変えていない）。
- **日時の列を含む読込（238 ms）**: 数値だけの同じ大きさの CSV（178 ms）より約 60 ms 長い。日時の認識（文字列の列ごとに、先頭 100 個の値で書式の候補を試す）と、10,000 個の文字列の日時への変換の分。設定変更からの更新（228 ms、デバウンス除く）は数値の X（215 ms）より約 13 ms 長い程度で、日時軸の目盛の計算の分とみられる。
- **貼り付け（10,000 行）180 ms**: 同じ大きさのファイルの読込（178 ms）とほぼ同じ。貼り付けたテキストは `pasted_data.tsv` というファイルとして、ファイルと同じ経路で読むため。
- **xlsx（2 シート × 10,000 行）の初回読込 843 ms**: ワークブックの解析（openpyxl）が大半。シートの切り替えでは、開いた `ExcelFile` を同じファイルの間だけ使い回すので、ワークブックを開き直さず、そのシートの読込と系列5本の描画だけで 465 ms になる。
- **2ファイル**: 読込はファイルごとに順に行う（208 ms。1ファイルの 178 ms に、2つ目の読込が約 30 ms 加わる）。設定変更からの更新は系列が2本なので、5本の既存項目より短い。
